01

What the project is

Start here. One pretend shop, one problem, one dashboard.

In one sentence

A pretend UK shop chain sells more every year but doesn't make more profit. This project finds out why, and what the managers should do.

The pretend company

NorthStar Retail UK: 24 stores + website + app, selling clothes, shoes, electronics, beauty, home, toys, sports, accessories.

Not a real company. A Python program created the data so it behaves like a real shop. Always say this in interviews.

The business problem

Managers get 4 reports that disagree (stores, website, finance, returns). Sales are up, but nobody knows where profit is lost.

Goal: one trusted set of numbers + a dashboard that answers what, why, where, what to do.

+15.7%sales growth 2024 → 2025
£3.96M → £4.58M
+9.4%profit growth only
−2.4pprofit per £1 of sales
43.3% → 41.0% margin

The 5 findings

  1. Too many discounts: 30%+ discounts leave almost no profit.
  2. Electronics: 19% of sales, only 6% of profit; loses money above ~19% discount.
  3. Costs rose faster than prices: suppliers +6%, prices only +3%.
  4. Online returns rising: clothes & shoes ~16% → ~27%, mostly one shoe brand (Stride Lab, wrong sizes).
  5. Two stores over-discount: Newcastle gives 3× the discount of other stores.

Why employers care

This is exactly what Data / BI Analysts do: messy data → clean → database → dashboard → decisions. It uses the tools UK adverts ask for: SQL, Power BI, DAX, Excel.

02

How it works: the pipeline

A chain. Each step takes the output of the step before it.

Step 0 · Business case

Define the question first

What: problem, stakeholders, KPI definitions (e.g. AOV = sales ÷ orders).

Why: every report must mean the same thing. Start with the question, not the chart.

Step 1 · Create data

A realistic pretend shop

What: 89,528 orders, 185,858 order lines, 12,500 customers, 1,220 products, 24 stores + online, 2 years.

Why: no real company data, so we simulate one with real patterns (Christmas, sales, online growth).

Step 2 · Make it messy

Break it in 37 counted ways

What: duplicates, "Web" vs "WEB", dates like 30 Feb, negative quantities, missing prices.

Why: real data is messy; cleaning is a key interview skill. Counting the mess means we can prove the cleaning works.

Step 3 · Clean it

Fix · flag · quarantine

What: 40 rules, each logged with a row count. 90 bad sales rows set aside (0.05%).

Why: wrong data → wrong decisions. Result: 100% of cleaned lines match the answer key.

Step 4 · Database

PostgreSQL star schema

What: 8 tables with keys and rules (quantity 1–20, net = gross − discount). 13 automatic checks, all PASS.

Why: the database itself refuses bad data, and every tool reads one source.

Step 5 · SQL

40 business questions

What: from "sales by category" to "which loyal customers stopped buying".

Why: SQL is the #1 analyst interview skill. Each answer is saved and explained.

Step 6 · Power BI

5 interactive pages

What: Executive, Sales, Profit, Customers, Returns; 52 DAX measures; filters on every page.

Why: managers click and filter themselves instead of waiting for reports.

Steps 7–8 · Findings & slides

Turn numbers into decisions

What: 10 insights (Finding → Evidence → Cause → Impact → Action → Outcome), impact-vs-effort ranking, 10 slides.

Why: charts alone don't help managers. Decisions do.

03

Data model: the star schema (UML / ER diagram)

Numbers in the middle (facts). Descriptions around them (dimensions). 1 = one, * = many.

Grain = what one row means

FactSales: one product line in one order. Count orders with DISTINCTCOUNT(OrderID), never row count.

Keys

PK Primary key = unique ID. → Foreign key = points to a dimension. Surrogate key = simple number we create (fast, stable).

Guest = −1

In-store shoppers with no loyalty card get CustomerKey −1. No sale is lost, and no "(Blank)" shows in slicers.

Two dates on returns

Return date = active link. Order date = inactive (dashed), switched on in DAX with USERELATIONSHIP.

Why Region is on the fact

Online orders ship from one hub with no region. Region = store region (in-store) or delivery region (online). One clear filter path, so no ambiguity.

Why a star schema?

Each description is stored once, Power BI is fastest with it, and it's simple: filter by dimensions, add up facts.

05

The important code, explained line by line

You don't need all 4,600 lines. These are the parts interviewers ask about. Full guide: CODE_GUIDE.md

sql/04_business_questions.sql · Q03 (line 47) 
1SELECT p.category,
2       ROUND(SUM(s.net_sales), 0) AS revenue,
3       ROUND(100 * SUM(s.net_sales)
         / SUM(SUM(s.net_sales)) OVER (), 1) AS revenue_share_pct,
       ROUND(SUM(s.gross_profit), 0) AS gross_profit,
4       ROUND(100 * SUM(s.gross_profit)
         / SUM(s.net_sales), 1) AS margin_pct
5FROM fact_sales s
6JOIN dim_product p ON p.product_key = s.product_key
7GROUP BY p.category
8ORDER BY revenue DESC;

Which categories make money?

  1. Show the category name as the row label.
  2. SUM adds up sales for each category pile.
  3. SUM(SUM()) OVER () = grand total on every row (window function), so each category ÷ total = its share.
  4. Margin = total profit ÷ total sales. Never average a margin column.
  5. Start with the sales table (185,858 rows). s is a nickname.
  6. Look up each sale's category in the product table, like an Excel VLOOKUP.
  7. Make 8 piles, one per category.
  8. Biggest sales first.

Result: Electronics = 19.3% of sales but 5.9% of profit (13% margin).

The database runs it in this order: FROM → JOIN → GROUP BY → SELECT → ORDER BY

sql/04_business_questions.sql · Q25 (line 379) 
1WITH m AS (
    SELECT d.year, d.month_number, d.month_short,
           SUM(s.net_sales) AS revenue
    FROM fact_sales s JOIN dim_date d ON d.date_key = s.date_key
    GROUP BY d.year, d.month_number, d.month_short
),
2w AS (
    SELECT *, LAG(revenue, 12)
              OVER (ORDER BY year, month_number) AS revenue_ly
    FROM m
)
3SELECT month_short, revenue_ly AS revenue_2024,
       revenue AS revenue_2025,
       ROUND(100 * (revenue / revenue_ly - 1), 1) AS revenue_yoy_pct
FROM w
4WHERE year = 2025;

Year-over-year growth for each month

  1. CTE (WITH m AS): a named temporary table holding one row per month with its sales.
  2. LAG(revenue, 12) looks 12 rows back, which is the same month last year. That's a window function.
  3. Growth % = this year ÷ last year − 1.
  4. Show only 2025 rows, where a "last year" exists.

Result: sales grew every month, but profit fell in January (−11%) and July (−4%), the sale months.

dax/measures.dax · Power BI formulas 
1Revenue = SUM ( FactSales[NetSales] )
2Gross Profit = [Revenue] - [Cost]
3Gross Margin % = DIVIDE ( [Gross Profit], [Revenue] )
4Orders = DISTINCTCOUNT ( FactSales[OrderID] )
5Customers =
    CALCULATE ( DISTINCTCOUNT ( FactSales[CustomerKey] ),
                DimCustomer[IsGuest] = "N" )
6Revenue PY =
    CALCULATE ( [Revenue], SAMEPERIODLASTYEAR ( DimDate[Date] ) )
7Revenue YoY % = DIVIDE ( [Revenue] - [Revenue PY], [Revenue PY] )

Measures recalculate for whatever is filtered

  1. Add up sales for the current filter (a year, a region, a bar you clicked).
  2. Measures can use other measures.
  3. DIVIDE = safe division (blank instead of an error when sales are 0).
  4. Count each order once, because one order has many lines.
  5. CALCULATE = "calculate, but change the filter": leave out anonymous Guest shoppers.
  6. Same dates, one year back. Needs the date table marked as a date table.
  7. Growth vs last year.

Filter context: written once, but Power BI calculates it separately for every bar, card and slicer choice.

scripts/03_clean_data.py · sales cleaning (line ~309) 
1s = s.drop_duplicates()
2CHANNEL_MAP = {"web": "Website", "website": "Website",
               "app": "Mobile App", "instore": "In-Store",
               "c&c": "Click & Collect", ...}
s["Channel"] = s["Channel"].str.lower().map(CHANNEL_MAP)
3assert s["Channel"].notna().all()
4s = quarantine(s, s["Quantity"] <= 0, "sales_transactions",
               "SA-06", "Negative quantity")
5fix = s["DiscountPct"] > 1
s.loc[fix, "DiscountPct"] = s.loc[fix, "DiscountPct"] / 100
6record("SA-09", "sales_transactions",
       "Discount entered as whole number", fix.sum())

Every rule: check → fix or set aside → log it

  1. Remove exact copies (a batch was loaded twice, which would double sales).
  2. 14 spellings of channels → 4 standard names. "WEB" → "web" → "Website".
  3. assert stops the program if any spelling wasn't mapped. Nothing slips through silently.
  4. Negative quantities are refunds typed as sales, so they're set aside in a quarantine file.
  5. "20" means 20%, so divide by 100.
  6. Write one line to the cleaning log: rule ID + how many rows.

Pattern: the 683-line file is this small pattern repeated for each table, plus building the star schema.

sql/01_create_schema.sql · the table rules 
1CREATE TABLE fact_sales (
    sales_line_key INTEGER PRIMARY KEY,
2    product_key INTEGER NOT NULL
        REFERENCES dim_product(product_key),
3    quantity SMALLINT NOT NULL CHECK (quantity BETWEEN 1 AND 20),
    discount_pct NUMERIC(5,4) CHECK (discount_pct BETWEEN 0 AND 0.6),
    net_sales NUMERIC(12,2) NOT NULL,
4    UNIQUE (order_id, order_line_number),
5    CHECK (net_sales = gross_sales - discount_amount)
);

The database protects itself

  1. Each row has a unique ID (primary key).
  2. Foreign key: a sale can't point to a product that doesn't exist.
  3. CHECK: quantity must be 1–20, discount 0–60%.
  4. No duplicate order lines.
  5. Maths must add up: net = gross − discount.

Real story: these rules caught 3 bugs while building, including sales dated before a product's launch.

The dashboard screens, and how each one works

5 Power BI pages, one per audience. Filters at the top work on every page. (Images are layout mockups; the real Power BI pages match this layout.)

Page 1 · for CEO & CFO

Executive Overview: "How are we doing vs last year?"

  1. Filters (top right): Year, Region, Channel, Category. Pick one and every visual updates.
  2. 7 KPI cards: Revenue, Gross Profit, Margin %, Orders, AOV, Customers, Return Rate. Each is one DAX measure.
  3. Revenue by month: line chart, 2024 (grey) vs 2025 (blue). Legend = DimDate[Year].
  4. Margin by month: shows profit per £1 falling, worst in sale months (Jan, Jul, Nov).
  5. Revenue by channel: click a bar to filter the whole page to that channel.
  6. Margin by category: Electronics stands out in orange (lowest).
  7. Check: the year table must show £3,961,750 (2024) and £4,584,138 (2025).
Page 2 · for retail & e-commerce heads

Sales Performance: "Where does revenue come from?"

  1. Revenue by region: sorted bar chart. London is the biggest (20%).
  2. Monthly revenue by channel: the app line grows fastest (+49%).
  3. Top stores: uses the measure Revenue (Physical Stores), so the online hub is excluded.
  4. Products table: sorted by revenue, with margin beside it, so best sellers with weak profit are visible.
  5. Like-for-like: stores open both years grew only +5.3%, which headline growth hides.
Page 3 · for CFO & category managers

Profitability: "Where is margin lost?"

  1. Cards: Margin %, change in points, discount given, profit lost on lines sold below cost.
  2. Margin by discount band: 46% with no discount, 6% at 40%+. Uses the calculated column Discount Band.
  3. Product scatter / table: Electronics products cluster at low margin.
  4. Margin by trading period: Black Friday, January and Boxing Day sales are the least profitable.
  5. Store margin league: Bluewater Outlet and Newcastle sit far below the rest.
Page 4 · for marketing & CRM

Customer Analytics: "Who are our valuable customers?"

  1. Cards: customers (Guests excluded with CALCULATE), revenue per customer, repeat %, guest share of store sales (~32%).
  2. Revenue per customer by segment: Premium spends about 2.7× more than Value.
  3. New vs returning by month: about 93% of orders come from returning customers.
  4. RFM segments: Champions = 55% of revenue; "At risk" = 1,450 loyal customers who stopped buying.
  5. Channel mix by age: younger customers shop more on the website and app.
Page 5 · for customer service & buying team

Returns: "What comes back, why, from which supplier?"

  1. Return rate by order month: uses the order-date measure (USERELATIONSHIP). The last month looks low only because returns haven't arrived yet (return lag).
  2. By category: footwear 15%, clothing 13%, beauty 1.5%.
  3. By reason: "Wrong size / fit" dominates clothes and shoes; "Faulty" dominates electronics.
  4. Margin before vs after refunds: website margin drops from 40% to 28%.
  5. Brands table: Stride Lab jumped from 10% to 28% returns in 2025.

09

Scenarios: what happens if…?

Use these to show you really understand how the parts connect.

Technical

A new spelling appears ("Webshop")

The CHANNEL_MAP has no match → assert stops the cleaning script with the unknown value shown. Add it to the map, re-run. Nothing wrong reaches the dashboard.

Technical

A batch is loaded twice

Rule SA-01 removes exact duplicates, and the database's UNIQUE(order, line) rule refuses any that slip through. Revenue never doubles.

Technical

The data folder moves (e.g. to D:)

Power BI shows "Could not find a part of the path". Fix: Transform data → Edit parameters → DataFolder = the new path ending with \ → Apply changes.

Technical

Next month's data arrives

Drop the new extracts in data/raw → run 03_clean_data.py → reload SQL → Refresh in Power BI. Same rules every time, which is why it's scripted, not done by hand.

Business

Manager selects "North East"

Every visual filters to that region. Margin drops to 38.6%, and the store chart shows why: Newcastle Eldon Square's heavy discounting.

Business

Cap Electronics discounts at 15%

2025 lines at ≥20% off made −£24.7K profit. At 15% off, losing 30% of those sales → about +£28K profit a year (illustrative, assumptions stated).

Business

December's return rate looks great

It isn't. Those orders haven't had time to come back (return lag). Never judge the latest month's returns at face value.

Business

"Total growth is +15.7%, stores are fine"

Not quite. Like-for-like stores grew only +5.3%; the new Sheffield store and online growth flatter the headline.

How to run it on a laptop

4 levels. Level 1 and 2 are enough to see everything working.

Level 1 · 15 min · no installs

Get it & see results

  1. GitHub → green Code → Download ZIP.
  2. Extract to C:\NorthStar\.
  3. In data, extract clean_data.zip here.
  4. Open the presentation, the Excel file, the screenshots.
Level 2 · 30 min · Windows

Open the Power BI dashboard

  1. Install Power BI Desktop (Microsoft Store). Close the sign-in box; no account needed.
  2. Open powerbi\NorthStar_Retail_Dashboard.pbip.
  3. Transform data ▸ Edit parameters ▸ DataFolder = your …\data\clean\ path.
  4. Apply changes / Refresh. Check page 1: £3,961,750 / £4,584,138.
Level 3 · 1 hour

Run the SQL

  1. Install PostgreSQL (includes pgAdmin).
  2. Create database northstar.
  3. Query Tool: run sql\01_create_schema.sql.
  4. Each table → Import/Export Data → CSV from data\clean, Header on. Dimensions first, then fact_sales, then fact_returns.
  5. Run 03 (all PASS) then 04.
Level 4 · 1 hour

Run the Python

  1. Install Python (tick "Add to PATH").
  2. VS Code → Terminal: pip install pandas numpy matplotlib openpyxl python-pptx
  3. python scripts\01_generate_data.py, then 02, then 03.
  4. Optional: python scripts\helpers\build_….py to rebuild the outputs.

The #1 problem you'll hit: the folder path

If Power BI says "Could not find a part of the path", search File Explorer for fact_sales.csv → right-click → Open file location → copy the address bar. On your laptop it was D:\Northstar\uk-retail-sales-bi-dashboard\data\clean\. No quotation marks, and keep the \ at the end.

15

Interview questions, with answers

Practise out loud in your own words. 50 more in notes/14_interview_question_bank.md

Is this real data?

No. A simulated UK retailer with synthetic data I generated, with realistic patterns. The methods are what I'd use on real data.

Why a star schema?

Descriptions stored once, simple for users, fastest in Power BI: filter by dimensions, add up facts.

What's the grain?

One row per order line. Orders = DISTINCTCOUNT(OrderID), not a row count.

WHERE vs HAVING?

WHERE filters rows before grouping; HAVING filters groups after totals are calculated.

How did you get YoY growth?

SQL: monthly CTE + LAG(revenue, 12). DAX: CALCULATE([Revenue], SAMEPERIODLASTYEAR(DimDate[Date])), then DIVIDE.

What does CALCULATE do?

Calculates a measure with changed filters, e.g. Customers without the anonymous Guests.

A data-quality problem you solved?

14 spellings of 4 channels, two date formats, a double-loaded batch. Mapping table, explicit date formats, de-duplication: validity 92% → 100%, only 0.05% set aside.

Did you delete blank customers?

No. Blank = no loyalty card in store, which is legitimate, worth £1.36M. Kept as a Guest member.

How do you know the numbers are right?

One reconciliation total (£8,545,888) every tool must match, 13 automatic database checks, and SQL vs Excel vs Power BI compared.

Most important insight?

Profit grew far slower than sales. I split the 2.4-point margin fall into cost inflation (1.6) and discounting (0.8).

30% off everything on Black Friday?

Electronics breaks even at ~19% off, so 30% loses money on every unit. Use category limits and test in a few regions.

How did you use AI?

"As a mentor and coding assistant. I ran everything, checked every number, and can explain any part. Pick a query and I'll walk you through it."
